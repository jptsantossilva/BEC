# Kraken Order Submission and Reconciliation Simplification

## Purpose

Make Kraken order confirmation fast and predictable without weakening durable
intent storage or duplicate protection:

```text
persist intent -> submit once -> Kraken returns txid
-> query txid after 1s, 2s and 4s
-> if unresolved, reconcile once per minute
```

The canonical schedule is named `orders_reconcile` and runs once per minute.
Startup migrates `orders_reconcile_15m` and `kraken_reconcile_15m` rows while
preserving their enabled state and `last_run`, then removes the obsolete rows.

## Interpretation of the 10:15 Telegram Messages

The messages shown at 10:15 were generated by scheduled reconciliation. They
mean BEC queried Kraken and persisted a filled result at 10:15; they do not show
that Kraken executed the orders at 10:15. Establish the actual timeline by
comparing, for each client order ID:

- `Orders.Date`, the intent creation/submission time;
- `Order_Fills.Filled_At`, the Kraken trade time when trustworthy;
- Kraken order/trade close or update time;
- `Orders.Last_Reconciled_At`, the confirmation/persistence time;
- `Raw_Response_JSON`, Kraken order history, and production logs.

## Implemented Lifecycle

1. Persist an immutable intent and increment `Submission_Attempts` once before
   the private submission.
2. Call Kraken `AddOrder` exactly once. Never retry submission automatically.
3. Persist a successful response containing a `txid` as `pending`, including
   `Exchange_Order_Id` and the raw acknowledgement. This operation neither
   applies fills nor sets `Last_Reconciled_At`.
4. If the submission response is terminal, apply it immediately. Otherwise,
   query that exact `txid` after cumulative delays of 1, 2 and 4 seconds.
5. Apply each returned result through the existing idempotent fill path. Stop
   after a terminal result, the third non-terminal result, or the first read
   exception/timeout.
6. Leave unresolved intents for the one-minute scheduled reconciler. The
   reconciler performs reads only and never submits or expires an intent.

Reconciliation returns before adapter construction when no unsettled intent
exists. It queries `Exchange_Order_Id` first and uses client-order/open/closed
search only if no `txid` exists or direct lookup cannot resolve it.

An identical unsettled action produces a structured `skipped` result and an
operator warning. The current trading cycle does not reconsider that action,
because its position data may be stale. The unique database index remains the
final concurrency safeguard.

## Permissions and Time Semantics

Kraken live keys require:

- Query Funds;
- Create/Modify Orders;
- Query Open Orders & Trades;
- Query Closed Orders & Trades.

Never grant withdrawal permission. Use an IP allowlist where possible. The live
preflight checks balances and both read-only order-history paths before an intent
can be created.

The existing schema retains these meanings:

- `Orders.Date`: intent creation/submission time;
- `Order_Fills.Filled_At`: Kraken trade time, when supplied by a trustworthy
  trade record;
- Kraken close/update time: reported separately when exact trade time is absent;
- `Last_Reconciled_At`: result confirmation and persistence time.

The order-open timestamp must never be presented as the execution timestamp.
One notification is sent only when a fill first changes the position. It shows
submission, execution or Kraken close, confirmation time, confirmation delay,
and either `immediate order query` or `scheduled reconciliation` as its source.

## Production Audit and Rollout

Before deployment, inspect both screenshot client IDs in `Orders`,
`Order_Fills`, `Raw_Response_JSON`, Kraken history, and production logs. Do not
infer execution time from the 10:15 Telegram delivery time.

Roll out in this order:

1. Disable Kraken buy/sell and every `main_*` job; keep reconciliation enabled.
2. Add the required read permissions to the API key and deploy.
3. Run the expanded read-only preflight.
4. Reconcile every existing intent.
5. Re-enable one side and one timeframe only.
6. Submit one operator-controlled minimum-valid order and verify one submission,
   confirmation within seconds, correct price/time/fees, one Telegram message,
   and no unsettled intent.

Rollback by disabling live flags and `main_*` jobs, keeping reconciliation
enabled, and deploying the previous image. There is no schema rollback.

## Validation

Focused automated coverage must prove acknowledgement persistence, all three
poll positions, timeout deferral, terminal rejection, a single submission
attempt, txid-first lookup, permission preflight, no-op reconciliation, duplicate
skip behavior, partial-fill idempotency, timestamp/message semantics, and
schedule-state preservation. Then run the full pytest suite, Python compilation,
documentation build, and a credential-free mocked/container configuration check.

## Exclusions

No schema migration, WebSocket execution feed, submission retry, adaptive
backoff, new persistent state, retroactive timestamp reconstruction, automatic
intent expiry, Binance behavior change, strategy/sizing change, cancellation
automation, simultaneous multi-exchange execution, or withdrawal permission is
included.
